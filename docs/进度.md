## 本周问题与解决（面试素材）

### 1. Redis AOF 写入失败导致 MISCONF，登录接口全挂

- **现象**：注册接口正常，登录接口统一返回 `B0001 系统异常`。
- **定位过程**：不是猜，而是三级排查 —— ① 看应用日志异常栈，发现 `MISCONF Errors writing to the AOF file: Input/output error`；② 用 `redis-cli` 直接 `SET` 复现同一错误；③ `INFO persistence` 查到 `aof_last_write_status:err`。
- **原因**：Redis 开了 AOF 持久化，写 AOF 文件失败后进入 **MISCONF 只读保护状态**：读命令照常，写命令一律拒绝。注册只写 MySQL 所以看不出问题，登录要写会话（`SETEX`）才暴露。
- **解决**：以 Windows 服务方式启动 Redis（`Start-Service redis`），而不是手工运行 `redis-server.exe`。
- **收获**：MISCONF 是 Redis 的自我保护而非故障本身；`aof_last_write_status` / `rdb_last_bgsave_status` 是排查持久化问题的第一入口。

### 2. Sa-Token 未登录异常被全局兜底吞掉

- **现象**：不带 token 访问接口，返回 `B0001 系统异常` 而不是 `A0006 未登录`。
- **原因**：`SaTokenExceptionHandler` 和 `GlobalExceptionHandler` 都能处理异常，但优先级不确定，`NotLoginException` 被兜底逻辑先接住了。
- **解决**：给 `SaTokenExceptionHandler` 加 `@Order(Ordered.HIGHEST_PRECEDENCE)`，明确异常处理器的优先级。
- **收获**：多个 `@RestControllerAdvice` 共存时，必须显式指定 `@Order`，否则异常被谁处理是"看运气"。

### 3. MyBatis-Plus 3.5.7 的 BaseMapper 方法重载导致单测编译失败

- **现象**：写 Mockito 单测时 `verify(mapper, never()).insert(any())` 编译报 "引用不明确"。
- **原因**：3.5.7 的 `insert` / `updateById` / `deleteById` 都有两个重载（单个对象 vs 集合），`any()` 无法推断类型。
- **解决**：显式指定类型，如 `any(TUser.class)`、`any(Long.class)`。
- **收获**：写 Mock 时尽量用带类型的匹配器，避免重载歧义，也更严谨。

### 4. 乐观锁拦截器类名拼写错误

- **现象**：启动报类找不到。
- **原因**：写成 `OptimisticLockingInnerInterceptor`，正确是 `OptimisticLockerInnerInterceptor`。
- **收获**：MyBatis-Plus 拦截器链（分页 / 乐观锁 / 防全表更新）注册顺序有讲究，类名要照官方文档核对。

### 5. Redis 序列化默认用 JDK 方式，存进去是乱码

- **原因**：`RedisTemplate` 默认 `JdkSerializationRedisSerializer`，key/value 都是不可读的二进制。
- **解决**：换成 `GenericJackson2JsonRedisSerializer`，Redis 里存的是可读 JSON，方便排查。

### 6. Spring Boot 3 的依赖必须用对应 starter

- MyBatis-Plus 3.5.7 必须用 `mybatis-plus-spring-boot3-starter`，用普通 starter 启动直接报错。
- Knife4j 4.5.0 必须用 `knife4j-openapi3-jakarta-spring-boot-starter`。
- **收获**：Spring Boot 3 迁移到 `jakarta.*` 命名空间后，第三方 starter 有专门的 boot3 版本，不能凭版本号想当然。

### 7. 数据库名不能用短横线

- **原因**：`short-link` 里的 `-` 在 SQL 中是运算符，建库/选库都要加反引号，容易踩坑。
- **解决**：统一用下划线 `short_link`。

### 8. 逻辑删除与数据隔离的设计约定

- 所有表用 `del_flag` + `@TableLogic`，删除是 `UPDATE del_flag = 1`，查询自动追加 `del_flag = 0`。
- 分组等资源接口全部做**归属校验**：先查记录，再比对 `username` 是否等于当前登录用户；**不区分"不存在"和"不属于你"，统一返回"分组不存在"**，避免通过错误信息探测他人资源是否存在。
- 密码用 BCrypt（每次加密结果不同，自带随机盐）；登录时"用户不存在"和"密码错误"返回同一个提示，**防止用户名枚举**。

## 第 2 周：核心（短链创建 + 跳转 + 缓存三件套 + 限流）

### W2D1 | Base62 与短链生成策略

**产出**

| 文件 | 作用 |
| --- | --- |
| `util/Base62Util.java` | `encode(long)` / `decode(String)` / `random(int)`，三者共用同一字符集常量 |
| `util/HashUtil.java` | `md5(String)` 生成 `origin_url_hash`，是 `uk_gid_origin(gid, origin_url_hash)` 的组成部分 |
| `util/LinkUtil.java` | 拼接完整短链 `{domain}/{gid}/{shortUri}` |
| `test/Base62UtilTest.java` | 编解码互逆、边界进位、随机字符集、10 万次去重率 |

改动：`GroupServiceImpl.generateGid()` 从「UUID 前 6 位」换成 `Base62Util.random(6)`。

**验收**

- `mvn test -Dtest=Base62UtilTest` 通过（4 个用例）
- 打印 10 个随机后缀，均为 6 位且数字/小写/大写混合：`uhUaQH buwKLN 5Nxf7j uwRMVs v3Yi3z e7gzRH PxxupR rccdRk WQHt88 b4BhXx`
- 10 万次随机去重率 > 99.99%

**思考题：6 位 Base62 能表示多少条？什么情况下不够用？**

- **理论上限**：`62^6 = 56,800,235,584`，约 **568 亿** 条。
- **随机方案的真实约束不是 568 亿，而是「碰撞重试」**：设已用 n 条，新生成一条撞上的概率约 `n / 62^6`。
  - n = 568 万（N 的 0.01%）时，单次碰撞率 0.01%，3 次重试后仍失败的概率约 `1e-12`，可以忽略；
  - n = 5.68 亿（N 的 1%）时，单次碰撞率 1%，3 次重试失败率约 `1e-6`，仍可接受；
  - n 再往上，重试次数和 DB 查询次数明显上升，写性能开始下降。
  - 所以**工程上把可用容量按 N 的 1% 量级估算**（百亿级理论容量 → 亿级实际容量）更稳妥。
- **什么时候不够用**：单个命名空间内的短链量接近千万~亿级、且写入并发高时，冲突重试会变成瓶颈。
- **扩容方案**：① 长度 6 → 8 位（`62^8 ≈ 218 万亿`），新旧短链长度不一致但业务无感知；② 用分组 gid 作为命名空间隔离容量（本项目 `t_link` 的唯一索引就是 `(gid, short_uri)`，已经天然按分组隔离）。
